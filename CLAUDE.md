# Правила разработки

Это долгосрочный проект.

Главная цель — получить качественный, легко поддерживаемый код.

## Общие правила

Работаем небольшими этапами.

Не реализовывать несколько крупных функций одновременно.

Если есть неоднозначность — сначала предложить варианты.

Не удалять существующий функционал без согласования.

Не менять архитектуру без объяснения причин.

## Код

Использовать Python.

Использовать Flask, если не будет веских причин предложить другой стек.

Использовать явную типизацию.

Соблюдать SOLID.

Не дублировать код.

Все настройки выносить в конфигурацию.

Не использовать магические числа и строки.

По возможности использовать dataclass.

Все публичные функции документировать.

## Архитектура

Проект должен быть максимально расширяемым.

Предпочитать композицию наследованию.

Разделять бизнес-логику, работу с базой данных и API.

Избегать больших классов.

## Git

После каждого законченного этапа делать commit.

Коммиты должны быть небольшими.

## Работа

Не пытаться реализовать весь проект за один шаг.

Перед началом реализации нового раздела сначала проанализировать существующий код.

Если видишь потенциальную проблему в архитектуре — сообщить заранее.

Если существуют несколько хороших вариантов реализации — предложить их пользователю и дождаться выбора.

## Что делать в первую очередь

Перед написанием кода:

1. Проверить документацию.
2. Проверить соответствие существующей архитектуре.
3. Предложить план реализации текущего этапа.
4. Только после подтверждения писать код.

# Примечание

Весь этот файл сгенерирован нейросетью как дополнение и расширение моих интуитивных требований к правилам работы над проектом. Соблюдай их. Также ниже прикладываю мой оригинальный текст. Наверняка он во многом дублирует вышесказанное, но  если увидишь что-то новое - эти требования тоже соблюдай. Вот текст:
1) Делаем один логический пункт за раз. Не нужно делать всё "с одного промпта" - скорее всего, получится с ошибками, потом будем долго мучительно исправлять
2) Не удаляй ничего и не меняй радикально, предварительно не спросив
3) Используй версионирование при помощи git, и делай коммиты почаще, чтобы можно было всегда откатиться к предыдущей версии (если вдруг что-то будет работать, а потом сломается)
4) Если где-то ты хочешь предложить мне выбор из нескольких хороших вариантов / не уверен в выборе и нужно мое мнение - останавливайся, предлагай и пиши.
5) Выноси все значения в переменные и клади их в config, чтобы для того, чтобы, условно, переименовать бота не пришлось переписывать весь код. Соблюдай SOLID, не дублируй код, не добавляй лишних зависимостей, используй явную типизацию - в общем, пиши хороший, чистый код, чтобы потом любой программист мог удобно вносить изменения даже в маленькие разделы (чтобы было понятно, как что менять, и не надо было прочитать весь код и разобраться со всеми зависимостями, чтобы добавить несложную функцию или, условно, поменять какое-то имя / какой-то фронтэнд)
